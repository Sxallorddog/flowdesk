Ты — senior full-stack developer, SaaS architect, product designer, UX/UI-дизайнер, database architect и специалист по информационной безопасности.

# FlowDesk

**FlowDesk — система управления клиентами, сделками и задачами для малого бизнеса.**

Это мой третий портфолио-проект после:

1. сайта и системы управления записями для стоматологической клиники;
2. интернет-магазина мебели с каталогом, корзиной и заказами.

Поэтому FlowDesk не должен повторять предыдущие проекты. Это должно быть настоящее веб-приложение, основной ценностью которого являются:

- сложная бизнес-логика;

# 1. Концепция продукта

Название:

**FlowDesk**

Описание:

**Простая CRM для небольших команд, которая помогает управлять клиентами, продажами, сделками и ежедневными задачами в одном месте.**

Основная проблема:

Малый бизнес часто хранит клиентов, задачи и сделки одновременно в таблицах, заметках, мессенджерах и памяти сотрудников. Из-за этого:

- теряются заявки;
- сотрудники забывают о следующем контакте;
- непонятно, на каком этапе находится сделка;
- задачи не имеют ответственных;
- руководитель не видит общую картину;
- информация о клиенте разбросана по разным местам.

Решение:

FlowDesk объединяет:

- базу клиентов;
- контакты;
- сделки;
- воронку продаж;
- задачи;
- комментарии;
- историю взаимодействий;
- активность команды;
- базовую аналитику.

Целевая аудитория:

- небольшие digital-агентства;
- студии дизайна;
- ремонтные компании;
- консалтинговые команды;
- рекрутинговые агентства;
- небольшие B2B-компании;
- фриланс-команды;
- сервисные компании с 2–30 сотрудниками.

FlowDesk должен быть достаточно универсальным, но демонстрационные данные оформи как рабочее пространство небольшой digital-студии.

Пример демонстрационной компании:

**Northline Studio**

Тип бизнеса:

Digital agency.

Команда:

- Owner;
- Sales Manager;
- Project Manager;
- Designer;
- Developer.

# 9. Multi-tenant архитектура

FlowDesk должен поддерживать несколько рабочих пространств.

Один пользователь может быть участником нескольких workspace.

Каждый workspace имеет отдельные:

- клиентов;
- контакты;
- сделки;
- pipeline;
- задачи;
- участников;
- настройки;
- активность;
- аналитику.

Данные разных workspace никогда не должны смешиваться.

Добавь переключатель рабочего пространства.

Пользователь должен видеть только те workspace, участником которых он является.

При каждом запросе проверяй:

1. Пользователь авторизован.
2. Пользователь является участником workspace.
3. Роль позволяет выполнить действие.
4. Запрашиваемый объект принадлежит этому workspace.

Нельзя доверять `workspace_id`, переданному с клиента, без серверной проверки членства.

# 10. Роли и права доступа

Роли:

## Owner

Может:

- управлять всеми данными;
- менять настройки workspace;
- добавлять и удалять участников;
- назначать роли;
- удалять workspace;
- управлять pipeline;
- просматривать всю аналитику.

## Admin

Может:

- управлять клиентами;
- управлять сделками;
- управлять задачами;
- приглашать участников;
- изменять большинство настроек;
- просматривать аналитику.

Не может:

- удалить владельца;
- удалить workspace;
- передать ownership без разрешения.

## Member

Может:

- просматривать доступных клиентов;
- создавать и редактировать назначенные ему сделки;
- создавать задачи;
- изменять свои задачи;
- оставлять комментарии;
- просматривать общую рабочую информацию.

Не может:

- управлять ролями;
- удалять workspace;
- менять критические настройки;
- удалять чужие данные без разрешения.

Создай централизованную систему permission checks.

Не разбрасывай проверки ролей случайно по компонентам.

Проверяй права как в интерфейсе, так и на сервере.

Скрытая кнопка не является защитой.

# 30. Row Level Security

RLS является обязательной частью проекта.

Создай политики, которые гарантируют:

- пользователь видит только workspace, в которых состоит;
- пользователь видит только данные этих workspace;
- Member не может менять роли;
- только Owner может удалить workspace;
- приглашение может принять только правильный пользователь;
- пользователь может редактировать собственный профиль;
- Storage ограничен workspace и владельцем файла;
- уведомления доступны только их получателю.

Не используй одну чрезмерно широкую policy вроде:

`authenticated users can access everything`.

Создай reusable SQL functions, если они упрощают проверку membership и roles.

Избегай рекурсивных RLS-политик.

Все критические операции дополнительно проверяй на сервере.

10. Вернуть типизированный результат.

Используй транзакции для операций, которые изменяют несколько связанных сущностей.

# Главный критерий качества

FlowDesk должен доказывать:

**Я умею проектировать и создавать полноценные SaaS-приложения с реальной бизнес-логикой, multi-tenant архитектурой, безопасным доступом, сложным интерфейсом и надёжной базой данных.**

Проект не должен восприниматься как:

- набор красивых dashboard-компонентов;
- статический макет;
- шаблон из UI-kit;
- frontend без backend;
- CRM, в которой кнопки ничего не делают.

Основной end-to-end сценарий должен работать полностью:

```text
Пользователь регистрируется
→ создаёт workspace
→ добавляет клиента
→ создаёт сделку
→ перемещает её по pipeline
→ назначает задачу
→ завершает задачу
→ видит историю
→ приглашает участника
→ участник получает ограниченный доступ
→ dashboard и аналитика обновляются реальными данными
```

Начни с архитектуры, permission matrix, базы данных и пользовательских сценариев. После этого последовательно реализуй продукт.
